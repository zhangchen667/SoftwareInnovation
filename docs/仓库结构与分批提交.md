# 仓库结构与分批提交

比赛仓库按软件组件组织，人员职责以[软件交付计划](分工与排期.md)为准。涉及多个组件的功能由各角色按接口协作。目录随对应组件的实现创建。

| 路径 | 主要维护人 | 内容 |
|---|---|---|
| `apps/android/`、`apps/wearable/` | C · 客户端开发 | 手机与腕端。若共用 Gradle 工程，可将腕端作为 Android 工程中的模块 |
| `apps/doctor-web/` | C · 客户端开发，D 协作 | 医生网页界面，D 提供服务与联调支持 |
| `services/api/` | D · 后端与系统集成 | 记录、任务、权限与计算调用，配套依赖及启动说明 |
| `algorithms/pose/`、`algorithms/texture/` | A · 算法与三维工程，D 协作接入 | 位姿结果、模型格式、纹理实现和基线。A 当前主做纹理，D 负责软件中的运行封装 |
| `examples/` | A、C、D | 可公开的合成模型、合成输入及接口样例，用于彼此联调 |
| `docs/` | B 统筹，四人更新 | 需求、原型、计划、接口、测试和发布说明 |
| `.local/`、`artifacts/` | 本机 | 私有输入、本地路径、计算缓存和生成模型，已被 Git 忽略 |

## 哪一批放什么

| 提交节点 | 可以提交 | 验收依据 |
|---|---|---|
| 立项与选型（当前） | 计划书、模块交接、合成 JSON、P2D 方案标识及来源说明 | 队友能定位当前方案，说清哪些已有、哪些本届开发 |
| 可安装的 Alpha | Android 工程、模型加载、演示服务或内置样例、构建与安装说明 | 能在另一台 Android 设备安装并完成一次查看。牙号和材质对应，演示数据来源可见 |
| 真实计算接入 | 任务封装、可配置路径、状态和接口。按授权迁入所需的既有实现、许可证及版本信息，以独立提交记录本届改动 | 从应用提交到读取结果可以完整操作。用 P2D 核对模型，覆盖任务失败和重试 |
| 可交付的版本 | 对应版本的源码、部署说明、可分发演示样例、测试与发布说明。APK 作为有版本号的构建产物 | 另一名队友按说明构建或安装，能复现演示。记录机型、依赖及软件版本 |

按实际完成时间提交。一次已经完成的历史导入可以放在一个清楚标记的提交里。导入说明记录来源、原作者或项目、形成时间或版本、授权范围、本次改动及验证；形成时间不清楚就写待核实。病例用于本机研究、向队友共享、公开演示与发布到 GitHub 是不同的使用范围。授权记录和原始材料留在受控位置。

## 竞赛仓库和正式提交

通知第 4 页要求本届期间完成作品的核心工作、关键组件和主要开发过程，还要求原创且作品未参加其他国家级公开比赛。Git 记录便于审阅贡献；GitHub 上传时间只表明文件何时进入该仓库。若学长的建模链或既有纹理占作品核心，队长应把继承的功能、授权和本届新增工作列清，向组委会询问具体方案是否符合规定，并保留回复。获得使用授权与满足本届原创条件应分别核实。

日常在短分支协作。交付比赛时，从确定的版本导出匿名材料，仅打包本阶段要求的内容，核查说明、截图、文件属性和内嵌路径。初赛计划书必交，程序及源码可选；区域复赛及决赛须提交 Beta 程序与源码。正式提交入口为赛事官网。[组委会通知正文，第 4–7 页](https://staticfile.eduplus.net/athena/richText/9ed9abcb41cc4cbda5351373a43fa9d1.pdf)
