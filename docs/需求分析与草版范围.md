# 需求分析与草版范围

2026-11-21 ｜ 团队讨论稿。项目整体方案见 [项目计划书](项目计划书.md)，每轮交付与分工见 [分工与排期](分工与排期.md)。

## 1. 用户、场景和待验证的问题

| 对象 | 典型场景 | 需求假设 | 怎样验证 |
|---|---|---|---|
| 正畸学生 | 复诊前回看之前的记录，想从不同角度看清整排牙 | 模型入口需要易找，旋转与缩放容易理解，稍后能找到同一条记录 | 让试用者拿到手机后自行找到一条演示记录、换个角度观察并重新打开。记录是否完成、发生过几次求助和卡住的页面 |
| 正畸学生 | 有新照片，想判断一次记录和上次的资料能否对照 | 照片来源、记录时间和可比范围需要容易理解 | 后续拿可比较与不可比较的样例，让试用者复述哪些是本次观测、哪些没有依据。对照原有相册使用习惯 |
| 医生 | 收到学生主动分享的一次随访及问题 | 先看到问题、记录时间和对应的照片或模型，再决定如何回复 | 访谈医生使用哪些信息复核。将授权后的记录交给试用者，观察能否定位到问题 |
| 有复诊担忧的学生 | 日常想随手记录感受，再回顾适合自己的选择 | 腕端记录能否减少操作负担，个性化选项能否根据反馈调整 | 先问真实使用习惯和设备，再用实机比较手机和腕端记录。记录参与或拒绝理由，以及哪些反馈改变了建议 |

当前依据是项目设想和已有三维研究，没有实际访谈结论。B 按 [项目计划书](项目计划书.md) 组织访谈，先了解最近一次真实记录和复诊经历，再给用户试用。首次测试先选队友试运行，拿到可用安装包后再邀请目标用户。发现的问题记录为“场景、观察、影响、对应需求、下轮改动和复验方式”。记录试用人数及样例属性，结论限于实际观察范围。

## 2. 草版目标与需求

**Alpha 面向内部试用，只验证一条完整体验：安装 APK，找到一条合成记录，打开并查看整排牙列，再次启动应用后从列表打开同一记录。** 默认随 APK 提供合成样例，草版不依赖账号、外网、GPU 或在线服务。该范围用于尽早验证操作体验和模型接入。

| 编号 | 优先级 | 用户需求和界面行为 | 验收标准 | 主责 / 协作 |
|---|---|---|---|---|
| F01 · 进入演示 | Alpha 必做 | 启动后能找到“演示记录”入口和至少一条可打开的记录。记录列表和详情都能看到“合成演示”来源 | 另一名队友在 Android 真机从 APK 安装开始，按页面提示找到记录。页面可区分演示与真实病例 | C / B、D |
| F02 · 查看整排 | Alpha 必做 | 点击记录打开整排模型，能拖动旋转、双指缩放。加载时有提示 | 通过手机操作看到正面和侧面。与样件参考图核对牙列完整、方向正确、材质可见 | C / A |
| F03 · 再次打开 | Alpha 必做 | 从详情返回记录列表，退出应用后仍可进入同一演示记录 | 离开应用并重新启动，打开同一记录 ID，仍加载对应模型。当前样例随包提供，可从默认视角开始 | C / D、B |
| F04 · 加载失败 | Alpha 必做 | 找不到模型或无法解析时显示可理解的原因和返回列表的入口 | 使用缺模型或损坏样例走到失败页，无闪退或永久等待。返回后仍能打开正常样例 | C / D、B |
| F05 · 从当前视角复位 | 体验优化 | 查看模型时可恢复默认观察视角 | 做旋转和缩放后复位，能回到进入详情时的视角 | C / A、B |

F01—F04 对应 [T01 草版真机验收](软件开发与验收.md#4-最小验收用例)，F05 按首轮试用决定是否纳入。Alpha 记录格式保持最小可读，至少约定记录 ID、来源、显示标题和模型引用。现有 [合成记录 JSON](../examples/visit.synthetic.json) 提供字段语义参考，尚需配上真实可加载的合成牙列或生成步骤。约定模型格式时用同一个样件核对模型、材质引用、默认视角和坐标方向。将列表和详情页与记录来源分开，后续由服务返回记录时沿用这套界面和显示字段。P2D 保留为 [科研对照基线](../algorithms/texture/README.md)，Alpha 的合成样件不用于比较纹理算法效果。

**Alpha 完成条件。** 从新装 APK 开始，在断开外网的 Android 真机跑通 F01—F04。执行者与构建者分开，记录手机型号、Android 版本、APK 版本和样件版本。留一份安装和操作说明、一次加载耗时记录、正常和失败两条验收记录。没有跑通的用例写明当前缺口。

## 3. 后续功能与排序条件

| 开发顺序 | 功能 | 进入迭代前需要什么 | 单独验收什么 |
|---|---|---|---|
| Alpha 后优先 | 实际建模任务、进度、失败与重试 | 可用于验证的输入和运行权限，算法依赖和最小接口已确认 | 从界面提交并得到当次计算的模型。依据运行日志确认不是预计算演示，失败可查，对应 T02、T03 |
| 有可比数据后 | 两期同视角对照、解释变化和不确定性 | 已确认同一人、牙号、坐标及可比范围，或用标识清楚的合成双期样例联调 | 指定牙在两期对应，实拍支持及未知区可辨。缺可信尺度时以模型单位展示，对应 T04 |
| 接服务后 | 记录授权与医生反馈 | 明确授权数据范围、目标医生和撤销行为 | 第二名医生不能访问，授权者撤销后服务端拒绝新请求，对应 T05 |
| 立即并行调研，实机条件确认后开发 | 腕端记录及反馈调整 | 可用设备、可实现的回传方式和访谈结果，能解释穿戴在场景中的作用 | 实机记录、选择与反馈后调整连贯，对应 T06。适用比赛要求见 [参赛依据](参赛依据.md) |

真实照片采集与建模、两期量化、医生端和穿戴实机交互列在后续范围。它们的需求会影响合成样例和接口设计，但当前 APK 以可操作的模型查看为验收目标。若 12 月初样例加载或安装还不稳定，优先修复阻断草版体验的问题，并保留已完成的版本供试用。
