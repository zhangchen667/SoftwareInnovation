# 四人分工与软件交付计划

2026-11-21 ｜ 团队讨论稿。A、B、C、D 为角色编号，成员认领和队长人选由团队确认。

目前已有可作为技术参考的三维科研程序和 P2D 纹理结果。团队要交付的是一款能在 Android 真机安装、通过界面使用、在另一台机器按说明部署的随访软件。采用短周期迭代，每轮选择一条能演示的用户流程，设计、实现、联调和验收。首轮范围见 [需求分析与草版范围](需求分析与草版范围.md)。

## 四个角色

| 角色 | 负责的工作 | 首周要交什么 |
|---|---|---|
| **A · 算法与三维工程** | 以纹理为主，维护 P2D 基线并比较后续效果。和系统开发约定现有三维程序的输入、结果格式、运行时间和失败条件，把模型及证据整理成可接入的结果。有余力再支援三维显示或联调 | 一份可分享的合成整排模型样件（或可生成样件的说明），注明牙号、坐标和材质。列出现有程序实际需要的输入、运行依赖和结果文件，和 D 走查一次 |
| **B · 产品设计与项目管理** | 做需求访谈、用户流程和交互原型，决定各版本范围并写验收用例，组织试用和缺陷复验。统筹计划书、演示脚本及提交材料 | 确认 F01—F04 的范围，画出“演示记录列表 → 模型详情 → 返回或失败”的原型，准备第一次真机试用步骤 |
| **C · 客户端开发** | 把原型做成可操作的界面，负责 Android 工程、三维交互、界面状态和 APK 构建。后续按产品范围接入其他终端界面，优先复用模型查看方式 | 给另一名队友一份可安装的 Android 空壳 APK，能从首页进入演示页。与 A、D 确认模型和任务状态怎样传给界面 |
| **D · 后端、系统集成与发布** | 把科研程序包成有稳定输入输出的计算任务，负责服务、记录存储及前后端联调。统一配置和启动方式，维护能在另一台机器部署的版本，和 C 产出整套发布包 | 先给 C 一份能和样件配对的本地记录及加载失败样例，明确其字段和模型引用。并行记录 Beta 需要的运行依赖和任务状态 |

测试贯穿各阶段。B 主持整体验收，其他成员分别提供本角色的实测记录。C 检查真机界面和安装，D 检查任务、存储与部署，A 核对模型、牙号和纹理质量。**集成由 D 负责，是否达到交付条件由 B 组织全队按用例确认。** 列表里的角色是职责归属，位姿、纹理、医生协作等功能要跨角色一起交付。

## 从科研程序到软件版本

1. **需求与设计。** B 带大家画出用户从打开应用到查看一条记录的流程，写出每一步结束时用户看得到的结果。C 和 D 确认哪些交互第一版能做，A 把已有程序的输入、输出及限制告诉两端。
2. **先完成可安装的 Alpha。** A 提供可分享的合成模型，D 提供与之对应的本地记录，C 把 Android 首页、记录入口、模型结果和失败提示连起来。由另一名队友在断开外网的 Android 真机安装 APK，查看整排、退出后再打开同一记录。
3. **接入实际计算，再扩展业务。** D 将输入检查、运行参数和输出路径做成可配置的调用，串起提交、运行、结果保存与查询。C 处理等待、失败和重新打开记录。A 核对软件读到的牙号、材质和覆盖信息。真实计算至少跑通一份可用于测试的输入，同一版本的演示样例要明确标示来源。手机与服务连通后，再迭代扩展场景。
4. **联调和测试。** 全组按“安装 → 打开应用 → 发起任务或选择演示样例 → 看结果 → 退出再回到记录”的用例跑一遍。检查不合要求的输入、任务失败、断网恢复和模型加载失败。加入分享后测试授权前、授权后与撤销后。记录版本、设备、复现步骤和修复后的结果。
5. **打包和发布。** C 提供签名 APK 与构建说明。D 配齐服务源码、依赖与配置示例、启动步骤和经确认可分发的演示数据。B 在非开发机上组织一次照着文档的安装和演示，核对计划书、测试记录、截图与视频使用同一版本。参赛材料按阶段要求导出，详见[参赛依据](参赛依据.md)。

## 每轮怎么更新计划

1. **选任务。** B 和队友看上一版的可用结果，从草版需求或后续功能中挑选本轮目标。对每个任务记一个负责人、输入来源、交给谁和完成标准。状态用“待做、进行中、待验收、完成”即可。
2. **做一版给人试。** A、C、D 用同一份样件和接口联调。D 记录集成版本，B 找非开发该流程的队友操作，记录实际结果和阻断问题。
3. **按反馈排序。** 先修导致任务无法完成、结果错误或容易误解的问题，再安排新功能。比如试用者能旋转模型却找不回历史记录，下一轮先修找回路径并重复 T01。新想法加到后续清单，由 B 在下轮计划时更新范围。后续换纹理方案由 A 和 C 用同一接口核对，保留基线对照。
