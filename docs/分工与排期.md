# 四人分工与软件交付计划

2026-11-20 ｜ 团队讨论稿。A 是当前负责纹理的同学，B、C、D 按各自擅长的方向认领。队长可由任一角色担任，建议与掌握排期和材料进度的同学对齐。

目前已有可作为技术参考的三维科研程序和 P2D 纹理结果。团队要交付的是一款能在 Android 真机安装、通过界面使用、在另一台机器按说明部署的随访软件。项目按需求与设计、开发、集成、测试、发布推进，每个阶段交付一个其他队友可以实际使用或检查的版本。

## 四个角色

| 角色 | 负责的工作 | 首周要交什么 |
|---|---|---|
| **A · 算法与三维工程（你）** | 以纹理为主，维护 P2D 基线并比较后续效果。和系统开发约定现有三维程序的输入、结果格式、运行时间和失败条件，把模型及证据整理成可接入的结果。有余力再支援三维显示或联调 | 一份可分享的合成整排模型样件（或可生成样件的说明），注明牙号、坐标和材质。列出现有程序实际需要的输入、运行依赖和结果文件，和 D 走查一次 |
| **B · 产品设计与项目管理** | 做需求访谈、用户流程和交互原型，决定各版本范围并写验收用例，组织试用和缺陷复验。统筹计划书、演示脚本及提交材料 | 一页需求与版本范围、一套低保真原型和一页验收步骤。原型包含启动入口、建模等待、结果页面和失败后可采取的操作 |
| **C · 客户端开发** | 把原型做成可操作的界面，负责 Android 工程、三维交互、界面状态和 APK 构建。后续按产品范围接入其他终端界面，优先复用模型查看方式 | 给另一名队友一份可安装的 Android 空壳 APK，能从首页进入演示页。与 A、D 确认模型和任务状态怎样传给界面 |
| **D · 后端、系统集成与发布** | 把科研程序包成有稳定输入输出的计算任务，负责服务、记录存储及前后端联调。统一配置和启动方式，维护能在另一台机器部署的版本，和 C 产出整套发布包 | 给 C 一份合成响应与调用样例，约定任务编号、处理中、完成、失败及结果引用。记录 GPU 和环境依赖，并明确本机私有输入怎样配置 |

测试贯穿各阶段。B 主持整体验收，其他成员分别提供本角色的实测记录。C 检查真机界面和安装，D 检查任务、存储与部署，A 核对模型、牙号和纹理质量。**集成由 D 负责，是否达到交付条件由 B 组织全队按用例确认。** 列表里的角色是职责归属，位姿、纹理、医生协作等功能要跨角色一起交付。

## 从科研程序到软件版本

1. **需求与设计。** B 带大家画出用户从打开应用到查看一条记录的流程，写出每一步结束时用户看得到的结果。C 和 D 确认哪些交互第一版能做，A 把已有程序的输入、输出及限制告诉两端。
2. **先完成可安装的 Alpha。** C 把 Android 首页、样例入口和模型结果页连起来。D 提供合成任务和示例响应，A 提供可分享的模型。验收时换一台 Android 手机，由另一名队友从 APK 安装开始，打开明确标为演示的数据、旋转整排模型并返回记录。
3. **接入实际计算，再扩展业务。** D 将输入检查、运行参数和输出路径做成可配置的调用，串起提交、运行、结果保存与查询。C 处理等待、失败和重新打开记录。A 核对软件读到的牙号、材质和覆盖信息。真实计算至少跑通一份可用于测试的输入，同一版本的演示样例要明确标示来源。手机与服务连通后，再迭代扩展场景。
4. **联调和测试。** 全组按“安装 → 打开应用 → 发起任务或选择演示样例 → 看结果 → 退出再回到记录”的用例跑一遍。检查不合要求的输入、任务失败、断网恢复和模型加载失败。加入分享后测试授权前、授权后与撤销后。记录版本、设备、复现步骤和修复后的结果。
5. **打包和发布。** C 提供签名 APK 与构建说明。D 配齐服务源码、依赖与配置示例、启动步骤和经确认可分发的演示数据。B 在非开发机上组织一次照着文档的安装和演示，核对计划书、测试记录、截图与视频使用同一版本。参赛材料按阶段要求导出，详见[参赛依据](参赛依据.md)。

## 排期与验收结果

| 目标日期 | 阶段 | 交付标准 |
|---|---|---|
| 11/26 | 需求和接口对齐 | 四个角色认领首周任务。拿到流程原型、初始 APK、样件及接口示例。同步确认穿戴设备条件、科研资产权限和校内报名节点 |
| 12/10 | Alpha 内测 | 一位队友能在独立 Android 真机安装，沿界面用样例完成“开启记录 → 查看和旋转模型 → 再次打开记录”。有启动说明和一次走查记录 |
| 12/24 | 可联调的 Beta | 接通实际计算，能从界面提交、查询和看到结果。按赛题与设备验证结果迭代完整随访流程，有一次双端或穿戴联调的实际记录。尚在开发的部分在计划书中按实填写 |
| 1/7 | 试用和修复 | 从安装开始做一轮用户试用，整理可复现的问题。按影响修复并复测，更新计划书及演示脚本 |
| 1/12 | 内部封版 | 锁定送测的代码版本，核查 APK、服务启动、演示样例和版本信息。完成匿名计划书。程序和视频以验收后的实际完成情况决定是否随初赛材料提交 |
| 1/15 18:00 | 区域初赛截止 | 队长提前提交，核对报名信息、上传文件和提交状态 |

第一次开会逐项确认四个首周产物由谁交给谁。每周用当前版本演示一条流程，记下本次可用环节、最影响使用的缺陷与下一次交付。B 维护排期，D 记录能复现的集成版本。后续换纹理方案时保留原模型接口与基线对照，由 A 和 C 确认新结果能在同一应用中正常打开。
